## 1. 已确认需求

本功能包含三个独立设置：

1. 新增第二组由用户自行录入的完整快捷键。用户连续两次触发该快捷键时，只唤出“快速窗口”。
2. 新增“全屏或窗口最大化时停用快捷键”，默认开启。
3. 新增“全屏或窗口最大化时停止记录复制内容”，默认开启。

准确的界面文字必须使用：

- `连按两次快捷键打开快速窗口`
- `全屏或窗口最大化时停用快捷键`
- `全屏或窗口最大化时停止记录复制内容`

不得把第一项写成“连按两次修饰键”。用户录入的是一组完整快捷键，例如 `Ctrl+Alt+K` 或 `Command+Option+K`，不是从 Ctrl、Alt、Shift、Win 等预设列表中选择一个键。

## 2. 产品行为定义

### 2.1 两组快捷键并存

保留现有的单次全局快捷键，并增加一组独立的“连按两次”快捷键：

| 设置 | 触发方式 | 默认值 | 结果 |
| --- | --- | --- | --- |
| 现有全局快捷键 | 按一次 | 保持现有平台默认值 | 打开快速窗口 |
| 连按两次快捷键 | 在规定时间内连续触发两次 | 未设置、未注册 | 只打开快速窗口 |

第二组快捷键要求：

- 不提供 Ctrl、Alt、Shift、Win、Control、Option、Command 等候选列表。
- 不提供预设组合键，也不自动替用户选择。
- 初始显示“未设置”；用户点击录入区域后，直接按下自己需要的完整组合键。
- 继续复用当前平台支持范围：至少包含一个修饰键和一个受支持的非修饰主键。
- 用户可以清除第二组快捷键；清除后立即取消原生注册并恢复“未设置”。
- 第二组快捷键不得与现有单次快捷键相同，否则第一次触发的含义无法确定，应用时必须拒绝并说明原因。
- 与其他应用冲突时保留上一组有效配置；如果此前未配置，则保持未设置。
- 录入、应用和清除第二组快捷键不能改变现有单次快捷键。

### 2.2 “连按两次”的精确定义

“连按两次快捷键”是两次完整的全局快捷键触发，不是键盘自动重复，也不是只按两次修饰键：

```text
按下完整组合键
  -> 松开
  -> 在允许时间内再次按下同一完整组合键
  -> 松开
  -> 打开快速窗口一次
```

时序要求：

- 第一次触发只进入等待状态，不打开任何窗口。
- 第二次在有效时间内到达时打开快速窗口一次，并立即清空等待状态。
- 超时后第一次触发作废，不执行任何动作。
- 第三次触发应作为下一组的第一次，不能与上一组第二次重叠计算。
- 按住快捷键产生的系统重复事件不能被当作第二次触发。
- Windows 两个注册槽都必须保留 `MOD_NOREPEAT` 语义；macOS 必须用原生测试和真实按键验证长按只产生一次有效触发。若平台仍产生重复事件，应在平台事件边界抑制，不能改成全局键盘 Hook 或监听所有用户按键。
- 应优先使用平台系统双击时间；为保证键盘体验，可将有效值限制在 250 至 700 毫秒。平台值不可用时使用 400 毫秒。
- 不在设置界面暴露时间参数，避免增加无必要的复杂配置。
- 使用可注入的单调时钟计算间隔，不能使用会受系统时间调整影响的墙上时钟。

### 2.3 只唤出快速窗口

第二组快捷键成功触发后只能走现有 `ShowQuickWindow()` 流程：

- 不打开主窗口。
- 不打开设置窗口。
- 不切换记录暂停状态。
- 不执行粘贴，仍由用户在快速窗口选择内容后决定复制或粘贴。
- 快速窗口已经存在时只激活并置于合适位置，不创建第二个快速窗口。
- 仍需先保存当前前台目标和屏幕，以保住现有自动粘贴流程。

命令行 `--quick`、托盘/菜单栏“快速粘贴”和应用内部按钮不属于“全局快捷键”，其行为不受第二组快捷键状态影响。

## 3. 全屏与最大化保护

### 3.1 保护对象

保护判断针对当前前台的外部应用窗口，例如游戏、视频播放器、远程桌面或最大化办公软件。SnapBoard 自己的主窗口、快速窗口和设置窗口不作为保护对象。

任意显示器上的前台窗口只要被明确识别为以下任一状态，就视为“受保护前台状态”：

- 操作系统原生最大化。
- 操作系统原生全屏。
- 覆盖当前显示器完整边界的无边框全屏。
- 能被平台可靠识别的独占全屏。

窗口只是尺寸较大、手工拖到接近屏幕边缘、贴靠半屏或覆盖工作区大部分区域时，不应误判为最大化或全屏。

多显示器下只判断当前前台窗口所在显示器，不要求它覆盖所有显示器。

### 3.2 全屏或窗口最大化时停用快捷键

该选项默认勾选，影响两组全局快捷键：

- 现有单次快捷键。
- 新增的连按两次快捷键。

行为要求：

- 保护状态下收到单次快捷键事件时直接忽略，不打开快速窗口。
- 保护状态下收到第二组快捷键第一次事件时不能进入等待状态。
- 第一次事件发生在普通窗口、第二次事件发生时已经进入保护状态，则取消本次双击序列，不打开快速窗口。
- 离开保护状态后快捷键立即恢复，无需重新注册或重启应用。
- 不应在进入全屏时注销系统快捷键；只在事件处理阶段抑制动作，避免其他应用抢占注册或反复注册失败。
- 设置窗口正在录入快捷键时，继续沿用当前逻辑吞掉已注册快捷键事件，不能弹出快速窗口。
- 托盘菜单、macOS 菜单栏、应用内按钮和第二实例 `--quick` 命令仍可明确打开快速窗口。

该选项只停用 SnapBoard 的快捷键动作，不拦截、吞掉或改写发送给前台应用的原始键盘输入。

### 3.3 全屏或窗口最大化时停止记录复制内容

该选项默认勾选。保护状态下检测到剪贴板变化时：

- 平台 watcher 继续运行并排空事件队列。
- 在调用 `IClipboardContentReader.ReadAsync` 之前停止该次采集。
- 不读取剪贴板正文、图片、文件路径或富文本。
- 不执行策略链、规范化、哈希、SQLite 写入、Blob 写入或同步 Outbox 写入。
- 不清空系统剪贴板，也不修改前台应用的复制行为。
- 不生成一条“被忽略内容”的历史占位记录。
- 离开保护状态后只记录之后发生的新复制事件，不补录保护期间的内容。

该选项只停止本机新剪贴板采集：

- 已有历史仍可搜索和使用。
- WebDAV 同步仍可上传此前的 Outbox，也可下载其他设备的历史。
- 历史保留清理仍可运行。
- 用户从 SnapBoard 主动复制或粘贴的现有流程不受影响。

### 3.4 自动保护与手动暂停必须分离

现有 `ClipboardCaptureCoordinator` 只有一个 `IsPaused` 状态。实现时必须区分至少两类原因：

- 用户手动暂停。
- 全屏/最大化自动保护。

状态组合：

| 手动暂停 | 自动保护 | 是否读取新剪贴板 | 离开全屏后的结果 |
| --- | --- | --- | --- |
| 关闭 | 关闭 | 读取 | 正常记录 |
| 开启 | 关闭 | 不读取 | 继续手动暂停 |
| 关闭 | 开启 | 不读取 | 自动恢复记录 |
| 开启 | 开启 | 不读取 | 继续手动暂停，不能自动恢复 |

要求：

- 离开全屏时不能无条件调用 `SetPaused(false)`，否则会覆盖用户的手动暂停。
- 托盘/菜单栏和主界面需要区分“用户已暂停”和“全屏保护中”。
- 自动保护不改变当前会话中的用户手动暂停状态。
- 用户关闭“全屏或窗口最大化时停止记录复制内容”后，如果没有手动暂停，应立即恢复采集。
- 存储迁移等内部暂停原因仍需独立保留，不能被全屏状态切换意外解除。

## 4. 前台窗口状态模型

### 4.1 新的平台抽象

当前 `IPlatformWindowPlacementService` 只负责屏幕定位和 SnapBoard 窗口位置，不应把游戏保护逻辑硬塞进窗口位置服务。建议新增单独的平台边界，例如：

```text
IPlatformForegroundWindowStateService
  -> GetForegroundWindowState()

ForegroundWindowState
  -> Normal
  -> Maximized
  -> FullScreen
  -> Unknown
  -> Unavailable
```

返回结果还应包含：

- 是否属于 SnapBoard 自己。
- 稳定的窗口/进程非秘密标识，供同一次判断避免竞态。
- 诊断码，不包含窗口标题、剪贴板正文或用户文档路径。

Desktop 只消费结构化状态，不直接引用 Win32、AppKit、Accessibility 或 CoreGraphics 类型。

### 4.2 Windows 判定要求

涉及现有区域：

- `SnapBoard.Platform.Windows/Desktop/`
- `SnapBoard.Platform.Windows/Interop/WindowsNativeMethods.cs`

应组合以下信号：

- `GetForegroundWindow` 获取当前前台 HWND。
- `IsZoomed` 明确识别普通最大化窗口。
- 窗口实际边界与 `MonitorFromWindow` 对应显示器边界比较，识别无边框全屏。
- 必要时使用 DWM 扩展框架边界，避免阴影和不可见边框造成误判。
- 排除无效、不可见、最小化、cloaked、桌面或 SnapBoard 自身窗口。

不得只用“窗口尺寸等于工作区”判定全屏，因为普通最大化窗口通常覆盖工作区而非包含任务栏的显示器边界。最大化与全屏都属于保护状态，但诊断与测试应保留两种分类。

### 4.3 macOS 判定要求

涉及现有区域：

- `SnapBoard.Platform.MacOS/Desktop/`
- `SnapBoard.Platform.MacOS/Interop/`

应组合可用的原生信号：

- 当前 frontmost application。
- 当前主窗口/焦点窗口的原生 full-screen 或 zoomed 状态。
- 窗口 frame 与所在 `NSScreen` frame/visibleFrame 的关系，用于补充判断无边框全屏。
- 多 Space 和原生全屏 Space 下的前台窗口身份。
- 排除 SnapBoard 自己、菜单栏面板、桌面和无有效前台窗口的情况。

如果某种检测需要 Accessibility 权限：

- 只能复用现有用户明确授权流程。
- 不得为了读取窗口标题而新增 Screen Recording 权限。
- 权限不足时返回 `Unknown` 和固定诊断码，不能猜测窗口状态。

### 4.4 Unknown 的处理

只有明确判定为 `Maximized` 或 `FullScreen` 才启用保护。`Unknown` 和 `Unavailable` 默认不阻断快捷键或采集，避免权限不足时 SnapBoard 永久不可用。

同时要求：

- 设置页显示“当前平台暂时无法判断前台窗口状态”或对应权限提示。
- 状态日志只记录固定诊断码，不能记录窗口标题。
- 原生平台测试必须尽量缩小 `Unknown` 的范围，特别是常见无边框游戏和视频全屏。

## 5. 设置与持久化

### 5.1 设置范围

以下设置属于设备本地设置，不随 WebDAV 空间同步：

- 现有单次全局快捷键。
- 新增连按两次快捷键。
- 全屏或窗口最大化时停用快捷键。
- 全屏或窗口最大化时停止记录复制内容。

理由：快捷键映射、键盘布局、游戏平台和窗口权限具有设备与操作系统差异。该边界与当前设置页的“本机设置保存在当前用户下；历史、隐私与同步频率随加密空间同步”一致。

不得把上述值写入 SQLite 的同步设置或生成 `SetSetting` Outbox 事件。

### 5.2 当前格式的全新默认值

| 设置 | 默认值 |
| --- | --- |
| 单次快捷键 | 当前产品定义的 Windows/macOS 默认 |
| 连按两次快捷键 | 未设置，不注册 |
| 全屏/最大化时停用快捷键 | `true` |
| 全屏/最大化时停止记录 | `true` |

SnapBoard 尚无正式用户。本功能不读取或迁移任何开发期快捷键键名、设置结构或损坏配置，也不做字段级补救。配置不存在表示全新安装，直接使用上表默认值；当前格式配置无法通过完整校验时明确拒绝该配置，并按当前格式重新初始化，不尝试保留其中的部分值。

### 5.3 平台存储

- Windows 继续使用当前用户下的 `HKCU\Software\SnapBoard\Desktop`。
- macOS 继续使用现有 `NSUserDefaults` 存储边界。
- 可以按当前设计统一调整键名和结构；不得为了开发期配置保留旧键读取或迁移分支。
- 第二组快捷键使用独立键名和可为空配置。
- 两个保护开关使用独立布尔值；平台存储失败只影响下次启动，当前会话应保留已应用状态并显示保存失败。
- 配置值必须有长度和范围校验，不能反射反序列化任意类型。

## 6. 设置界面要求

### 6.1 快捷键区域

继续使用现有 `SettingsWindow` 的快捷键录入控件样式，不增加预设菜单。

建议布局：

```text
全局快捷键
用于从任意窗口打开快速窗口

打开快速窗口
[ Ctrl+Shift+V                         ] [应用] [恢复默认]

连按两次快捷键打开快速窗口
[ 未设置 / 用户录入的完整组合键       ] [应用] [清除]

快捷键至少需要一个修饰键；两组快捷键不能相同。
```

交互要求：

- 两个录入器同一时间只能有一个处于“录入中”。
- 点击第二个录入器后，下一组完整组合键进入待应用状态。
- `Esc` 取消当前录入并保留原值。
- 单独按修饰键时保持录入状态，不将其保存为快捷键。
- “清除”使用熟悉的清除/删除图标并带 Tooltip；清除当前有效绑定前应立即解除第二组原生注册。
- 第二组未配置时不显示“恢复默认”，因为不存在预设默认值。
- 第二组与第一组相同时，“应用”不可成功，并显示“两组快捷键不能相同”。
- 发生系统注册冲突时显示“快捷键已被其他应用占用，原配置已保留”。
- 文案统一使用“快速窗口”，不要在该设置行写成“主窗口”或“修饰键”。

### 6.2 全屏保护区域

在常规设置中新增一个不嵌套卡片的独立设置组，例如“全屏保护”：

```text
全屏保护

[开] 全屏或窗口最大化时停用快捷键
     避免游戏、视频或远程桌面被快速窗口打断

[开] 全屏或窗口最大化时停止记录复制内容
     保护期间仍监听变化，但不会读取或保存剪贴板内容
```

要求：

- 使用现有 `settings-toggle` 风格。
- 两项首次显示均为已勾选。
- 切换后当前会话立即生效，无需统一“保存设置”按钮。
- 说明文字必须能换行，不能在 660 px 最小宽度下溢出。
- 设置窗口保持滚动布局，不通过继续增加固定窗口高度解决内容增加。
- macOS 当前生命周期中的平台专属固定高度不得遮挡新增设置。

### 6.3 状态反馈

当自动保护生效时：

- 主窗口记录状态显示“全屏保护中，暂不记录”。
- Windows 托盘和 macOS 菜单栏显示与手动暂停不同的状态。
- 离开保护状态后恢复原来的正常或手动暂停状态。
- 快捷键被全屏保护拦截时不弹出窗口、通知或系统提示，避免打断游戏。
- 可在设置页显示当前检测状态，但不得显示前台窗口标题或应用文档名称。

## 7. 运行时流程

### 7.1 单次快捷键

```text
平台收到 Primary hotkey
  -> 设置窗口是否正在录入？是：忽略
  -> “全屏时停用快捷键”是否开启？
       -> 否：ShowQuickWindow
       -> 是：读取前台窗口状态
            -> Maximized/FullScreen：忽略
            -> 其他：ShowQuickWindow
```

### 7.2 连按两次快捷键

```text
平台收到 Double hotkey
  -> 设置窗口是否正在录入？是：清空序列并忽略
  -> 全屏快捷键保护是否命中？是：清空序列并忽略
  -> 当前是否有未超时的第一次触发？
       -> 否：记录本次单调时间，等待第二次
       -> 是：清空序列，ShowQuickWindow 一次
```

窗口被打开、设置改变、快捷键重新注册、应用进入退出流程或服务释放时，都必须清空未完成的双击序列。

### 7.3 剪贴板采集

```text
ClipboardMonitor 产生变化
  -> 继续排空平台事件队列
  -> 用户手动暂停？是：跳过正文读取
  -> 存储迁移/内部暂停？是：跳过正文读取
  -> “全屏时停止记录”开启？
       -> 否：读取并进入现有采集链
       -> 是：读取前台窗口状态
            -> Maximized/FullScreen：跳过正文读取
            -> 其他：读取并进入现有采集链
```

前台状态检查失败不得终止唯一 watcher，也不得把原生异常详情写入 UI。

## 8. 与现有代码的落点

以下是实施时必须检查的实际边界，不表示现在修改：

| 现有文件/符号 | 当前状态 | 后续任务 |

## 10. 手工验收矩阵

至少在以下真实场景验证：

| 场景 | 快捷键保护 | 记录保护 | 预期 |
| --- | --- | --- | --- |
| 普通窗口 | 开 | 开 | 两组快捷键和记录均正常 |
| 最大化浏览器/IDE | 开 | 开 | 两组快捷键不弹窗，复制不入历史 |
| 窗口化游戏 | 开 | 开 | 未最大化时正常工作 |
| 无边框全屏游戏 | 开 | 开 | 不弹窗、不读取剪贴板 |
| 独占全屏游戏 | 开 | 开 | 可检测平台不弹窗、不读取；无法检测必须记录限制 |
| 全屏视频 | 开 | 关 | 快捷键不弹窗，但复制仍可记录 |
| 最大化窗口 | 关 | 开 | 快捷键可打开快速窗口，但复制不入历史 |
| 最大化窗口 | 关 | 关 | 两项功能都正常工作 |
| 手动暂停后进入/离开全屏 | 任意 | 开 | 离开后仍保持手动暂停 |
| 全屏时托盘/菜单栏打开 | 开 | 任意 | 明确用户操作仍可打开快速窗口 |

Windows 建议覆盖：普通桌面应用、浏览器、IDE、无边框游戏、独占全屏游戏、远程桌面和多显示器。

macOS 建议覆盖：Safari/Chrome、全屏视频、原生全屏 Space、zoomed 窗口、游戏、多 Space、多显示器和权限允许/拒绝状态。

## 11. 性能、安全与 AOT 门槛

- 前台状态查询不能在空闲时高频轮询；快捷键在事件到达时查询，剪贴板只在变化事件到达时查询。
- 如需短时缓存，缓存必须足够短并在前台应用变化时失效，不能让离开全屏后长期保持保护。
- 不记录前台窗口标题、游戏名称、文档路径或剪贴板内容。
- 不使用按进程名称维护“游戏列表”的方式判断全屏。
- 原生句柄、AX/CG 对象和 Win32 资源必须明确释放。
- 双击状态机不得为每次触发创建长期 Timer；使用单个可取消计时状态或时间戳判断。
- Windows 和 macOS Native AOT 发布保持 0 个未解释 trim/AOT 警告。
- 不引入程序集扫描、反射配置序列化或第三方键盘 hook 框架。
- Windows 继续优先使用 `RegisterHotKey`，macOS 继续使用现有 Carbon 注册边界；不得为双击功能改成读取所有用户键盘输入。

## 12. 完成定义

实现阶段只有满足以下全部条件才能标记完成：

- [ ] 第二组快捷键完全由用户录入，没有预设修饰键菜单或默认组合键。
- [ ] 界面文字为“连按两次快捷键打开快速窗口”。
- [ ] 两次触发只打开快速窗口一次。
- [ ] 两组快捷键可独立注册、保存、恢复、清除和处理冲突。
- [ ] 两个全屏/最大化保护选项默认开启并即时生效。
- [ ] 快捷键保护覆盖 Primary 和 Double，但不影响菜单、按钮和 `--quick`。
- [ ] 记录保护在读取剪贴板正文之前生效。
- [ ] 手动暂停、自动保护和内部暂停不会互相覆盖。
- [ ] Windows 与 macOS 均通过自动测试和真实全屏场景。
- [ ] 全量 Release build、test、format、Native AOT 均通过且无未解释警告。
- [ ] `PLAN.md` 与 `docs/PROGRESS.md` 记录实现证据和未覆盖的游戏/显示器限制。

### 13.2 不得缩减的实现范围

- 最终功能范围必须同时覆盖 Windows 和 macOS，但按第 13.4 节分两个阶段实施：先完成 Windows 与共享层并合入 `main`，再由 macOS 环境从更新后的 `main` 追平。Windows 阶段不能用空实现或虚假测试把 macOS 标记为完成。

- 第二组快捷键完全由用户录入，没有预设列表、默认组合键或自动推荐。
- 按住、键盘自动重复、Primary 与 Double 混合触发均不能完成第二组双击序列；不得引入全局键盘 Hook。
- 全屏记录保护必须在 `IClipboardContentReader.ReadAsync` 前生效。手动暂停、全屏自动保护和存储迁移/更新安装等内部暂停必须由不同原因位持有，清除一个原因不能解除其他原因。
- `Unknown` 和 `Unavailable` 默认放行；不得记录窗口标题、游戏名称、文档路径或剪贴板内容。
- 全屏快捷键保护只抑制两组全局快捷键，不能影响托盘/菜单栏、应用内按钮和 `--quick`。
- SnapBoard 尚无正式用户，不实现开发期快捷键键名、设置结构或业务数据的兼容、迁移和字段级补救。
